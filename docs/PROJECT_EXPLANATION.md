# Project Explanation for Beginners and Viva Preparation

This guide explains what the project actually does, using the real code and results in this repository. Numbers quoted here come from `outputs/` and the notebook; if you retrain with different library versions they may change slightly.

---
## 1. Problem statement
A factory machine that breaks unexpectedly stops production. We want a program that looks at a machine's current readings (temperatures, speed, torque, tool wear) and says **how likely it is to fail**, so engineers can inspect high-risk machines first.

In machine-learning terms this is **binary classification**: predict `Machine failure` = 1 (fails) or 0 (does not fail), and also give the probability.

## 2. Business use case
Maintenance teams have limited time. A good system flags the right machines:
- **False negative** (a failure the model missed): downtime, damage, safety risk. Expensive.
- **False positive** (a false alarm): someone inspects a healthy machine. Cheaper, but too many false alarms make people ignore the system.

So we care about **recall** (how many failures we catch) and **precision** (how many alerts are real), not just accuracy.

## 3. Dataset and features
File: `data/ai4i2020.csv`, 10,000 rows, no missing values, no duplicates. It is a **synthetic** dataset (generated by the dataset authors to look like real machine data).

- **Inputs we use:** `Type` (L/M/H), air temperature, process temperature, rotational speed, torque, tool wear.
- **Target:** `Machine failure`.
- **Not used:** `TWF, HDF, PWF, OSF, RNF` (failure *types*) and `UDI, Product ID` (identifiers).

**Why exclude the failure types? (data leakage).** These flags say *why* a machine failed. 330 of the 339 failures have one of them set. They are only known after the failure is diagnosed, so a real system cannot use them. If we included them the model would score almost perfectly in the notebook but be useless in practice. This is called **data leakage** and detecting it is one of the most important skills in the project (see notebook section 7 and `core.LEAKAGE_COLUMNS`).

Only 339 of 10,000 rows (3.39%) are failures, so the data is **imbalanced**.

## 4. Data preprocessing
Done inside a scikit-learn **Pipeline** (`build_pipeline` in `train_model.py`):
1. `FunctionTransformer(core.add_features)` creates the new features (section 6).
2. `ColumnTransformer`: `StandardScaler` for numeric columns (rescales each to mean 0, spread 1, which helps Logistic Regression and the neural network) and `OneHotEncoder` for `Type` (turns L/M/H into three 0/1 columns because models need numbers).
3. The classifier.

**Why a pipeline?** The scaler learns the mean and spread from the *training* data only. If it also saw the test data, information would leak from test to training. Inside a pipeline, `fit` is called on training data only and the test data is just transformed. Single predictions in the web app go through exactly the same saved pipeline, so the app and training can never disagree.

**Splitting:** `train_test_split(test_size=0.2, stratify=y, random_state=42)`. 80% (8,000 rows) to train, 20% (2,000 rows) to test. `stratify` keeps the 3.39% failure rate in both parts. `random_state=42` makes it repeatable.

## 5. Exploratory data analysis (EDA)
The notebook has 10 visualizations. Key findings (all computed from the data):
- **Tool wear:** failure rate is about 2-3% up to 200 minutes, then **15.5%** above 200.
- **Torque and speed:** failures cluster at high torque / low speed and very low torque / high speed. Speed and torque are strongly negatively correlated (-0.875).
- **Torque outliers** (69 rows): 89.9% fail. We **keep** outliers because they hold the signal.
- **Temperatures:** air and process temperature are almost the same signal (correlation 0.876), but their **difference** matters: all 115 rows with a small difference (under 8.6 K) and low speed (under 1,380 rpm) failed.
- Linear correlations with failure are weak (largest is 0.19), but the patterns are strong thresholds and interactions, so straight-line models struggle.

## 6. Feature engineering
Defined once in `core.add_features`:
| Feature | Formula | Idea |
|---|---|---|
| `temp_diff_K` | process temp - air temp | how well the machine sheds heat |
| `power_W` | torque x rpm x 2π/60 | mechanical power |
| `wear_x_torque` | tool wear x torque | worn tool under heavy load |

These are built only from inputs available at prediction time, so they do not leak the target.

## 7. The four algorithms (and what they did here)
| Model | Idea in one line | Strength | Weakness | Result (test set) |
|---|---|---|---|---|
| **Logistic Regression** | Weighted sum of inputs turned into a probability | Simple, fast, interpretable | Only straight-line boundaries | Weakest: recall 0.588, precision 0.357 |
| **Decision Tree** | A flowchart of yes/no questions | Very easy to explain | Can overfit; coarse probabilities | Recall 0.824, precision 0.918 |
| **Random Forest** | Many different trees voting | Handles interactions, robust | Less transparent, bigger file | Recall 0.868, precision 0.720 |
| **ANN (MLPClassifier)** | Layers of connected neurons | Flexible, learns complex patterns | Needs more data, hard to explain | Recall 0.794, precision 0.607 |

(Check the exact current figures in `outputs/model_comparison.csv`.)

## 8. Hyperparameter tuning
**Hyperparameters** are settings you choose before training (for example tree depth). `GridSearchCV` tries every combination in a grid, using **5-fold cross-validation**: the training data is split into 5 parts; the model trains on 4 and is scored on the 5th, five times. The best combination (by PR-AUC) wins. The grids are in `model_spaces()` in `train_model.py`; the chosen values are on the Model Performance page.

## 9. Evaluation metrics
- **Accuracy:** share of all predictions that are correct. Misleading here: "always predict no failure" scores 96.6%.
- **Precision:** of machines we flagged, how many really failed. `TP / (TP + FP)`.
- **Recall:** of machines that really failed, how many we flagged. `TP / (TP + FN)`.
- **F1:** balance of precision and recall. **F2:** same but recall counts 4 times more (our choice, because misses are costlier; this weighting is an assumption).
- **ROC-AUC:** how well the model ranks failures above healthy machines (1.0 = perfect, 0.5 = random).
- **PR-AUC:** same idea using precision and recall; more honest for rare events.

## 10. Confusion matrix
A 2x2 table of results on the test set:
|  | Predicted no failure | Predicted failure |
|---|---|---|
| **Actually no failure** | TN (correct) | **FP** (false alarm) |
| **Actually failure** | **FN** (missed failure) | TP (caught) |

For the selected Random Forest: 1909 TN, 23 FP, 9 FN, 59 TP.

## 11. False positives vs false negatives
Lowering the **threshold** (the probability above which we raise an alert) catches more failures but creates more false alarms. We chose each model's threshold on training data to maximise F2. The notebook plots this trade-off. Selected Random Forest threshold: 0.345, so anything at or above 34.5% probability is flagged.

## 12. Final model selection
The rule: highest cross-validated F2 on the **training** data (PR-AUC breaks ties). The test set is not used to choose, so it gives an honest final check. This selected **Random Forest**.

Be ready to say honestly: with only 68 failures in the test set, the Decision Tree and Random Forest are close (the tree has fewer false alarms: 5 versus 23, and a slightly higher test F2). A different team could defensibly choose the tree for its simplicity.

## 13. Flask architecture
```
Browser  <-->  app.py (routes)  <-->  core.py (validation, features, Predictor)  <-->  models/*.joblib
                    |
                 templates/ + static/ (HTML, CSS, JS)           outputs/*.json,*.csv (dashboard numbers)
```
- `train_model.py` trains and saves. `app.py` only **loads** (`joblib.load` inside `core.Predictor`). Flask never retrains.
- `create_app()` builds the app and loads the model once at startup.

## 14. How the frontend talks to the backend
Standard web forms, no hidden APIs:
1. Browser requests `GET /predict`; Flask renders `predict.html` (the form).
2. You press submit; the browser sends `POST /predict` with the six values.
3. Flask calls `core.validate_record` (rejects bad input with field messages) then `predictor.predict_one`.
4. Flask renders the same template again with the result.
Charts on the dashboard are drawn by `static/js/charts.js` from JSON embedded in the page by Jinja (`|tojson`).

## 15. How the saved model produces a prediction
`train_model.py` saves a dictionary with `joblib.dump`: the **fitted pipeline**, the **threshold**, training ranges and medians. At prediction time `Predictor.predict_frame`:
1. selects the columns in the fixed order `core.RAW_FEATURES`,
2. calls `model.predict_proba` (the pipeline engineers features, scales, encodes, then the forest outputs a failure probability),
3. marks failure if probability >= threshold,
4. assigns a risk band: High (>= threshold), Medium (>= threshold/2), Low (below). This rule is project-defined, not an industry standard.

The "which inputs matter" panel is a what-if test: replace one input by its training median and see how the probability changes (`Predictor.local_effects`). It is an approximation, not proof of cause.

## 16. Batch prediction workflow
`POST /batch`:
1. Check a file was sent, ends with `.csv`, is not empty (size limit 2 MB enforced by Flask).
2. Read it **in memory** with `pd.read_csv(io.BytesIO(...))`; the filename is never used to build a file path, so path traversal is not possible, and nothing is saved to disk.
3. `core.validate_batch`: required columns present (no duplicates), at most 5,000 rows, each row's numbers valid and in range. Bad rows are listed by CSV line number; good rows continue.
4. `predictor.predict_frame` scores all valid rows with the **same** function used for single predictions (a test checks both give identical probabilities).
5. The results page shows a table sorted by probability; *Download* returns every row as CSV from memory.

## 17. Limitations
Synthetic data; only 339 failures; probabilities are estimates; risk bands and the F2 weighting are assumptions; the app keeps history in memory only and runs on the Flask development server. See the README.

## 18. Viva questions and model answers
**1. What problem does the project solve?** It estimates each machine's probability of failure from operating readings so maintenance can focus on high-risk machines first.

**2. Why not use accuracy?** Only 3.39% of rows are failures, so predicting "no failure" every time gives 96.6% accuracy but catches nothing. I used recall, precision, F1/F2, PR-AUC and the confusion matrix.

**3. What is data leakage and where did you find it?** Using information that would not exist at prediction time. The failure-mode columns (TWF, HDF, PWF, OSF, RNF) describe why a machine failed; 330 of 339 failures have one set, so they were excluded. I also excluded identifiers.

**4. Why did you keep outliers?** Torque outliers are failures 89.9% of the time; removing them would delete the signal.

**5. Which features did you engineer and why?** Temperature difference (heat dissipation), mechanical power (torque x speed) and wear x torque (overstrain). The EDA showed failures depend on such combinations.

**6. How did you prevent preprocessing leakage?** Scaling and encoding are inside a `Pipeline`, fitted on training data only (a unit test checks the scaler's mean equals the training-set mean).

**7. What is cross-validation?** Training/validating on rotating parts of the training data (5 folds) to get a more reliable estimate and to choose hyperparameters without touching the test set.

**8. How did you handle class imbalance?** Class weights for the three models that support them, threshold tuning for all models (the MLP has no class-weight option), and imbalance-aware metrics.

**9. What is a decision threshold and how did you choose it?** The probability above which we raise an alert. I picked, per model, the value that maximises F2 on out-of-fold training predictions.

**10. Why F2?** Recall counts four times as much as precision because a missed failure is assumed to cost more than a false alarm. The 4:1 ratio is my assumption, not a measured cost.

**11. Why did you choose Random Forest?** Best cross-validated F2 on training data and the best ranking metrics (ROC-AUC 0.987, PR-AUC 0.880) with the highest recall (0.868). The Decision Tree is close with fewer false alarms; with only 68 test failures the difference may be chance.

**12. Why did Logistic Regression do badly?** Failures follow thresholds and interactions (tool wear above 200 min, torque/speed extremes). A straight-line boundary cannot capture that.

**13. Did the neural network not win?** No. The dataset is small and tabular, where tree ensembles often do as well or better, and the MLP is harder to explain.

**14. Explain precision and recall with your result.** For Random Forest: of 82 machines flagged, 59 really failed (precision 0.72); of 68 real failures, 59 were flagged (recall 0.87).

**15. What does ROC-AUC mean?** The chance that a random failing machine gets a higher score than a random healthy one. 0.987 means almost always.

**16. Why PR-AUC as well?** With rare failures, ROC-AUC can look good even when precision is poor. PR-AUC focuses on the rare class.

**17. How does Flask use the model?** `core.Predictor` loads the saved joblib file once at startup. Routes validate input, call `predict_proba`, and render templates. The model is never retrained by the app.

**18. How is batch prediction safe?** Extension and size checks, in-memory processing, filename never used for paths, column and value validation, row limit, no permanent storage.

**19. How are risk categories decided?** High at or above the threshold (0.345), Medium at or above half of it, Low below. It is a project convention and not an industry safety standard.

**20. What does the dashboard show and is any value hard-coded?** Historical counts and charts from `outputs/dataset_stats.json`, model results from `evaluation_metrics.json`, importance from `feature_importance.csv`, all written by `train_model.py`. Session predictions are shown separately and are never counted as historical failures.

**21. What would you improve with more time?** Real data and time-series features, cost-based threshold, calibrated probabilities with confidence intervals, SHAP per prediction, a database and production deployment.

**22. How can you tell the app really uses the trained model and not hard-coded values?** `tests/test_app.py` compares the page's probability with `Predictor.predict_one`, checks single and batch outputs agree, and checks dashboard numbers equal the values in the saved JSON.

**23. What are the weaknesses of your evaluation?** Single test split with 68 failures, so wide uncertainty; synthetic data; assumed cost weighting.

**24. What does the what-if panel mean?** The change in probability if one input were replaced by its typical training value. It hints which inputs drive the estimate but is not a causal explanation.
